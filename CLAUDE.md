# Logic Detective

Noir deduction game. Procedurally generated cases; a solver guarantees exactly one culprit per case. Portfolio project: single-player first, multiplayer later.

## Core design
- Cases are generated from the truth: pick a culprit and traits (hat, coat color, location, item), generate clues that are all true of the culprit, then have the solver confirm exactly one suspect fits. Regenerate if not (`verifyCase` in lib/solver.js is the final gate).
- Four levels (`LEVELS` in lib/data.js): 5 to 8 suspects, from direct clues up to negative and relational clues.
- Style: flat-color noir. Shapes, emoji and inline SVG only; no image assets.

## Modes
`generateCase({ seed, level, mode })`
- `'pool'` (single-player): the player picks from a shuffled pool of face-down cards (`poolSize` per level: 6/7/8/10), labelled by category only until opened. Every card is true of the culprit and rules out at least one suspect: no decoys. `par` is the smallest subset of the pool that identifies the culprit (brute-forced); it is stored on the case and never sent to clients.
- `'race'` (default; for multiplayer): an ordered deck revealed one clue at a time. Each clue narrows the field when revealed, but the deck is NOT guaranteed to be the smallest set (a later clue can make an earlier one redundant). Never claim every race clue is necessary. A timed reveal (one clue per 10-15s) is planned, not built.
- Race output must stay unchanged: `test/race-golden.test.js` compares against `test/fixtures/race-golden.json`.
- Level fields: `minClues` is the floor on solution-deck length (both modes). `minPar` is the pool-mode floor on par, and it is also the par shown on screen and used for scoring. They differ at levels 3-4 because a strong card caps par at floor(n/2).

## Run rules (single-player)
- A run is 4 cases, levels 1 to 4 in order. Wrong accusation = a strike. Strikes accumulate across the whole run; the third ends it.
- Open at least `MIN_CARDS_TO_ACCUSE` (2) cards before accusing (enforced in the adapter).
- Opening a card never eliminates anyone; the player crosses suspects off by hand (UI-only notes).
- Scoring lives only in lib/scoring.js (`SCORING`, `scoreCase`, `scoreBreakdown`, `scoreRun`). UI code may read `SCORING` constants for display text but must not compute scores or re-implement the par/bonus rules. The leaderboard server recomputes scores with `scoreRun`; it never reads a client-sent total.

## Layout
- /lib       shared rules, plain ESM with no Node-only APIs (data, rng, clues, solver, generator, view, scoring, text with `clueToText`, leaderboard with the nickname and run validation). Runs in the browser and on the server.
- /server    server-only logic using web-standard APIs only (`fetch`, `Request`/`Response`, WebCrypto): `upstash.js` (REST client), `leaderboard.js` (store, rate limit), `scores.js` (handler), `memoryRedis.js` (in-memory stand-in for tests and `DEV_MEMORY_STORE=1`). Never copied to public/.
- /api       Vercel route files, kept thin: `scores.js` exports `GET` and `POST` and calls `handleScores`. Put logic in /server, not here (any file in /api may become a function).
- /scripts   build.js, dev.js (`npm run dev`; also serves /api/scores and reads .env.local), sample.js, pool-stats.js.
- /public    static front end: index.html, css/, js/ (main.js UI, gameClient.js adapter, dom.js `h()` builder, nameForm.js, leaderboardClient.js, leaderboardView.js, art.js, storage.js, config.js).
- /public/lib is generated by `scripts/build.js` (copies lib/*.js so the browser can import them) and is gitignored. `npm test` runs the build first (pretest); Vercel runs it via vercel.json (`buildCommand`, `outputDirectory: public`).
- /public/js/gameClient.js is the adapter and the only thing the UI talks to: `startRun`, `getCase`, `openCard`, `accuse`, `nextCase`, `getRunSummary`. All run state and rules go through it. It is what gets swapped for fetch calls to /api later, so keep its methods and return shapes stable.
- /test      node:test suites, plus fixtures/.
- Deploy: Vercel from GitHub on push to main (planned; no project is connected yet). vercel.json only builds and serves public/; /api functions are picked up from the project root. That this coexists with `outputDirectory`, and that Vercel bundles imports from /lib and /server, has not been confirmed on a real deployment: check on a preview. Separate from other projects.

## No-leak and seed rules
- Nothing the leaderboard stores or returns may contain a culprit, par or seed (tests check requests, stored entries and responses). UI code never touches the culprit, a case's computed par, or the seed. (The par it displays is the level's `minPar`, which the adapter hands over.) Until a case ends, nothing returned by `publicView` or the adapter may contain the culprit, the seed, or unopened clue text, even after `JSON.stringify`. Tests enforce this (test/view.test.js, test/gameClient.test.js); keep them passing.
- Seeds come from `crypto.getRandomValues` (the adapter, and the default in `lib/rng.js`), never a counter, the date, or `Math.random`. The seed decides the answer, so it must not leave the server or adapter. In multiplayer, seeds are generated and kept on the server only.

## Leaderboard
- It is HONOR-SYSTEM: the game runs in the browser, so a client can always lie about a run. The server makes lying costly, not impossible, and nothing may claim otherwise.
- `POST /api/scores` takes `{ name, cases: [{ level, cardsOpened, wrongAccusations, solved }] }` and nothing else (the browser never sends a total, par or seed). The server validates the run (`lib/leaderboard.js`: at most 4 cases, levels in order, at most 3 strikes, cards between `MIN_CARDS_TO_ACCUSE` and the level's pool size, only runs the rules can produce) and recomputes the score with `scoreRun`. `GET /api/scores` returns the top 20. Redis keeps the best 100; rate limit 10 submissions per hashed IP per hour.
- Nicknames: 2-16 of letters, numbers, space, hyphen, underscore (ASCII), plus a small best-effort blocked-words list. A nickname is optional; the game must work without one and with storage blocked. Player-supplied text is rendered only as text nodes (`h()` text, `textContent`), never `innerHTML`; a test enforces it.
- Redis: plain `fetch` to the Upstash REST API using ONLY `KV_REST_API_URL` and `KV_REST_API_TOKEN` (server-side only; documented in `.env.example`). Do not use `KV_REST_API_READ_ONLY_TOKEN`, `KV_URL` or `REDIS_URL`. If the variables are missing or Redis fails, the API answers 503 and the rest of the game keeps working.
- Tests never need Redis: they inject `memoryRedis.js`. Keep it that way, and keep `npm test` dependency-free.
- Locally: `npm run dev` serves /api/scores (503 without Redis); `DEV_MEMORY_STORE=1 npm run dev` uses an in-memory board; `.env.local` with the two variables uses the real Redis.

## Multiplayer phase (later)
- 2-8 players join by room code; clients poll `/api/state` every 1-2 seconds.
- State in Upstash Redis (same two variables and `server/upstash.js` client as the leaderboard). The server only sends clues revealed so far, never the answer.
- 3 rounds ramping through levels 2, 3, 4; a new clue every 10-15 seconds (tune in play). Players race to accuse; earlier correct accusations score more.

## Working rules
- For any new generator or solver logic, write and test it before any UI.
- `npm test` stays dependency-free (Node 20+) and generates 1000 random cases per level, asserting each has exactly one valid culprit.
- Keep game logic free of UI code so it can run on the server.
- Commit in small, descriptive steps. Never commit secrets; use `.env.local` and `.env.example` (`.gitignore` ignores `.env*` except `.env.example`).
- Open PRs, but never merge them.
